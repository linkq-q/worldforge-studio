# 植物园渲染性能复查（2026-09-25）

## 结论与更正

不能用“有反射/折射/泛光”“有几百万累计三角形”解释当前性能。上一轮尚未测 GPU，也未做游戏实现对照，把剔除列为主要方向的证据不足。

本轮固定整图可见的俯视镜头，保持资产、地图、效果和分辨率不变。诊断性禁用不透明 BatchedMesh 的部件排序后，CPU 采样中位数从 24.6 ms 降至 16.0 ms；绘制调用与三角形完全相同。这直接证明存在可观的 CPU 绘制准备成本，不需要先减少资产或关闭画面效果。

这是一份诊断报告。下述实验开关与插桩已从正式运行路径移除，没有把实验实现作为正式修复提交，也没有修改地图、保存画质设置。

## 实验条件

- 基线提交：`c115c0d`；工作区包含原有地形/规划未提交修改。
- 页面：本地 WorldForge 编辑器，当前已保存的植物园，580 个地图物体。
- 图形后端：ANGLE / NVIDIA GeForce RTX 5060 Laptop GPU / Direct3D11 / WebGL 2。
- `WEBGL_multi_draw` 与 `EXT_disjoint_timer_query_webgl2` 均实际可用。不能把缺少 multi-draw 支持当作这台机器的原因。
- 编辑器画布 drawing buffer 固定为 **888 × 671**，DPR=1；关闭诊断页的自适应画质调整。该条件用于因果对照，不代表 1080p/4K 性能。
- 相机固定于 `[0,240,100]`，朝向 `[0,0,0]`；截图确认整张地图处于视野中。
- 保留当前已加载的水面、阴影、泛光及其他渲染效果，没有改变物体数量、网格精度或剔除设置。
- 页面加载后至少 15 秒才采样；每 30 帧采样一次；四种条件每 15 秒轮换，覆盖多个周期。
- CPU：在 `RenderSceneRuntime.renderFrame` 首尾计时；另测 `BatchedMesh.onBeforeRender`、`renderBufferDirect` 与矩阵更新。函数插桩有自身开销，所有对照使用相同插桩。
- GPU：异步 `TIME_ELAPSED_EXT` 查询，仅在结果可用后读取；检查 disjoint；不调用 `gl.finish()`。这是 GPU 命令时间线区间，不是显卡纯忙碌时间/利用率，可能含 CPU 供给不足导致的空隙。CPU 与 GPU 时间不能相加。
- 帧间隔：相邻渲染开始时刻之差，包含浏览器调度；不等同于 CPU 执行耗时。

## 最终对照统计

下表均为采样中位数；样本数量差异来自各条件帧速率不同与读取窗口边界。

| 条件 | 样本数 | CPU ms | GPU 查询 ms | 帧间隔 ms | 批次准备 CPU ms | draws | 累计 triangles |
|---|---:|---:|---:|---:|---:|---:|---:|
| 基线 | 58 | 24.6 | 20.008 | 25.0 | 10.0 | 807 | 3,387,450 |
| 仅取消不透明部件排序 | 66 | 16.0 | 13.218 | 17.9 | 2.5 | 807 | 3,387,450 |
| 仅禁止水背景采集重画阴影 | 35 | 22.5 | 19.189 | 24.1 | 8.8 | 715 | 2,878,214 |
| 两项同时启用 | 60 | 14.5 | 12.101 | 16.0 | 2.1 | 715 | 2,878,214 |

最有力的对照是前两行：绘制内容和规模不变，CPU 中位数下降约 35%。不能把所有 GPU 查询下降都解释为 shader 算得更快，因为 CPU 提交节奏也改变了。

### CPU 排序路径

- `vendor/voxel-render-runtime/src/batching/BatchedPrimitiveGroup.js` 创建 `THREE.BatchedMesh`，没有覆盖默认的 `sortObjects=true`。
- 当前 `node_modules/three/src/objects/BatchedMesh.js` 的 `onBeforeRender` 每次遍历部件、获取变换及包围球、计算距离、排序并重建 multi-draw 列表。
- 同一采样帧记录到 60 次 `BatchedMesh.onBeforeRender`。主画面、阴影、法线/深度、水背景采集都可能触发这条准备路径。
- 诊断变体仅在当前 pass 材质不透明时将 `sortObjects` 暂设为 false，调用原方法后还原；没有关闭逐部件视锥剔除。透明排序保留。
- 因此“已经合批”并不代表 CPU 无须再遍历部件。这是当前项目与高吞吐渲染实现之间一个已经测到的具体差距。
- 正式优化仍须检查不透明表面遮挡较强的近景、透明材质、共面表面，以及排序改变后 GPU overdraw 的代价；此处不声称该实验对所有地图均有相同收益。

### 阴影重复更新

- `WaterSceneCapture.render()` 调用 renderer.render 时没有禁止阴影自动更新。
- 同一帧的水背景采集记录到 92 个阴影 draws / 509,236 triangles；主画面又记录到 121 个阴影 draws / 511,680 triangles。
- 这是同一个太阳光源的两次更新；两次投影物集合并不完全相同，因为背景采集暂时隐藏透明物体。
- 实验禁止采集阶段更新阴影后，draws 恰好减少 92。首轮该变体有明显波动，重复轮换后最终中位数如表所示，收益小于取消排序。
- 不能直接把“采集用上一帧阴影”作为正式解决方案：移动投影物、光照变化及首帧都需要正确的资源更新次序。应验证一次完整阴影更新后供各通道复用。

### 泛光与各通道

固定 888×671、独立逐通道 GPU 查询的一组约 20 帧样本：

| 区间 | CPU 调用均值 ms | GPU 查询均值 ms |
|---|---:|---:|
| 水背景采集（包含其阴影） | 5.52 | 4.22 |
| 法线/深度预绘制 | 2.82 | 1.89 |
| 主画面（包含其阴影） | 10.27 | 6.93 |
| 泛光内部 12 次全屏绘制合计 | 约 0.14 | 约 0.15 |

泛光行仅为其具名 bright/blur/内部合成 targets，不包含最后写回主画面的混合操作。即使如此，这组测量不支持“泛光是主要瓶颈”。各通道 CPU 数据用于定位准备开销，不构成 GPU 纯运算成本分解。

## 与公开游戏实现的对照

### 《都市：天际线》一代

参考的是实际资产作者编写的 [CS I Modding Building Asset Creation](https://cslmodding.info/asset/building/#lod-mesh)，不是官方引擎源码或本机帧捕获。文档描述：远景使用独立简化网格；LOD 贴图合入 atlas；缺少自定义 LOD 时游戏尝试生成。

这说明它在俯视时可以保持整座城市可见，同时减少每个可见物体的表示成本；不需要把它解释成大量隐藏物体。但该资料没有给出可与本项目等条件比较的 CPU/GPU 帧时间，也不足以证明 LOD 是本项目当前主要瓶颈。

### 《刺客信条：大革命》与 RedLynx

育碧渲染开发者 Ulrich Haar / Sebastian Aaltonen 的 [SIGGRAPH 2015 GPU-Driven Rendering Pipelines](https://advances.realtimerendering.com/s2015/aaltonenhaar_siggraph2015_combined_final_footer_220dpi.pdf)：

- 第 13 页：静态实例数据持久存于 GPU buffer，按材质/渲染状态组织批次；后续工作包括 GPU 侧实例/cluster 处理。
- 第 36 页（ACU 部分）：实例量约为前作 10 倍，报告的相关 CPU 时间约为前作 75%，draw calls 降低 1–2 个数量级。
- 第 52–53 页（RedLynx 独立测试，不能混称 ACU 实机）：250,000 个运动对象的测试场景，Xbox One 1080p 下报告 GPU 2.3 ms、CPU 0.2 ms。表格对应该几何/G-buffer 测试管线，不是完整游戏最终画面或所有后处理的总成本。

可借鉴的是降低每个部件、每个通道重复的 CPU 工作。不能把该论文的绝对 ms 直接拿来要求本项目达到同样数字，也不能把 WebGL multi-draw 等同于完整的 GPU-driven pipeline。

### 《孤岛惊魂 5》水面

开发者 [SIGGRAPH 2018 The Challenges of Rendering an Open World in Far Cry 5](https://advances.realtimerendering.com/s2018/The%20Challenges%20of%20Rendering%20an%20Open%20World%20in%20Far%20Cry%205%20%28With%20Notes%29.pdf) 第 14 页说明，系列此前使用平面反射；FC5 希望支持倾斜河流，并复用世界已有的屏幕空间反射，讨论了将水面与已有数据/渲染管线整合。

本轮该大 PDF 全文下载未成功，以上仅据搜索工具返回的该页原始讲稿摘录核实。不能据此宣称已审计 FC5 完整管线。

## 验证边界与下一步

- 没有在这台电脑上启动《都市：天际线》或 3A 游戏抓同条件帧；本轮完成的是公开实现对照与本项目控制变量实验，不是跨游戏硬件 benchmark。
- 不能宣称 580 个资产已达硬件上限，也不能以“多个效果/多个 pass”解释卡顿。
- 第一优先级应是经过测量的 BatchedMesh 准备/排序路径：在不影响透明正确性前提下减少不必要排序，并评估静止镜头时列表缓存。
- 第二优先级是正确组织太阳阴影更新和复用；不能直接保留会导致动态阴影延迟的诊断开关。
- 俯视场景的新增剔除暂不作为已证实的高收益方向。是否需要 LOD，应独立测试网格成本后决定。
- 本轮不包含正式行为变更，未重新运行整套测试/构建；临时插桩和实验开关已移除，保留本报告。
